# EduForge 前端设计基线

## 1. 文档定位

本文是 EduForge 稳定前端产品、视觉、交互与 UX 原则的 Owner，用于约束后续页面、组件、布局、样式和用户可见交互。

- 当前前端工程结构和能力范围由 [Frontend snapshot](./handoff-frontend-snapshot.md) 维护。
- 当前路由、API 对接和组件职责分别由 [route map](./handoff-frontend-route-map.md)、[API map](./handoff-frontend-api-map.md) 与 [component map](./handoff-frontend-component-map.md) 维护。
- 本文不冻结具体 Tailwind class、色值或组件实现，也不把尚未实现的未来产品方向写成当前设计事实。

## 2. 当前产品与界面基线

EduForge 当前前端包含公开介绍入口与教师、学生角色工作区；角色工作区共用轻量页面骨架、清晰标题层级和可复用的导航、空状态、错误状态与标签页模式。

- 教师端围绕课程、班级、任务、提交、反馈和教学分析组织工作。
- 学生端围绕加入班级、查看任务、完成提交和理解反馈组织路径。
- 当前视觉以浅色、中性、低装饰和高可读性为主；设计基线延续这一整体一致性，但不把现状误称为完整设计系统。

## 3. 核心产品原则

1. **教学任务优先于技术术语**：页面首先表达用户要完成的教学动作、对象、状态和下一步，不让 API、DTO、内部 ID、raw enum 或实现机制占据主要信息层级。
2. **信息层级清晰**：页面标题、上下文、主要状态、主要操作和辅助信息应有稳定顺序；复杂页面先给结论和行动入口，再按需展开细节。
3. **角色目标明确**：教师端服务快速判断与教学干预，学生端服务任务完成与反馈理解；同一技术能力应按角色使用目标呈现。
4. **一致性优先**：页面调整优先复用现有 Shell、PageHeader、Tabs、EmptyState、ErrorState、任务上下文和既有表单/动作模式。
5. **渐进改进**：没有明确产品收益时，不进行大范围视觉重写、布局体系替换或装饰性升级。

## 4. 教师端 UX 基线

- 优先呈现班级、任务、学生、提交和反馈的当前状态，以及教师可以立即采取的下一步行动。
- 看板与分析页面应帮助教师快速识别需要关注的对象和可执行干预，不用原始数据堆叠替代判断支持。
- 高频教学动作保持清晰可达；归档、删除、恢复等低频或高影响动作降低默认视觉权重，并保留明确确认与结果反馈。
- 统计与 AI 分析使用克制、可解释的教学语言，不把代理指标写成正式成绩、能力结论或因果判断。
- 复杂详情应保留来源、上下文和返回路径，避免教师在跨课程、班级、任务和提交时失去定位。

## 5. 学生端 UX 基线

- 优先提供从“看到任务”到“完成提交”再到“查看反馈”的连续路径，减少不必要分支和认知负担。
- 每个关键页面应突出一个主要下一步；辅助操作不得与任务主动作争夺视觉优先级。
- 截止、提交资格、处理进度、失败和可重试状态应使用学生能够理解的语言，并给出明确下一步。
- 空状态、错误状态和权限边界应说明发生了什么以及用户可以做什么，不要求学生理解内部实现机制。
- 反馈呈现优先帮助学生理解问题和改进方向，不以状态枚举、内部标签或调试数据作为主内容。

## 6. 视觉与布局原则

- 延续当前浅色背景、中性色层级、清晰边框和克制状态色；颜色服务于层级、状态和错误识别，不服务于装饰。
- 保持稳定内容宽度、合理留白和可扫描的信息分组；标题、说明、操作区和主体内容避免挤在同一视觉层级。
- 卡片、表格和列表按信息结构使用，不为了制造“仪表盘感”堆叠容器。
- 错误、警告和成功状态不能只依赖颜色表达；关键状态同时提供文字或明确语义。
- 页面与组件应延续现有响应式收缩和换行方式；响应式范围、局部滚动与横向溢出约束见 [§6.1](#61-响应式与设备兼容基线)。
- 动效保持少量、短暂且有功能目的，不用复杂转场掩盖状态变化或增加等待感。

## 6.1 响应式与设备兼容基线

教师端和学生端均必须响应式支持下列手机、平板和桌面范围，包括平板横竖屏及 viewport 动态变化。所有尺寸均指实际 CSS content viewport：`window.innerWidth × window.innerHeight`；这些是代表性设计/验收 viewport，不是 CSS breakpoint 清单，也不要求穷举所有设备型号。

| 设备范围 | 代表性 viewport |
|---|---|
| 手机竖屏 | `390×844` |
| 大屏 Android 平板竖屏 | `800×1280` |
| 大屏 Android 平板横屏 | `1280×800` |
| 大屏 iPad 竖屏 | `1024×1366` |
| 大屏 iPad 横屏 | `1366×1024` |
| 紧凑桌面 | `1280×720` |
| 桌面大屏 | `1536×864` |

- 页面不得产生 document / main 级无意横向溢出；Grid、Flex、Card 等子项应允许合理收缩，多栏布局在窄屏下应自然收缩、重排或切换为单列，不得通过固定宽度把主要页面撑出 viewport。
- 表格及确需保留最小内容宽度的密集区域可以在明确的局部容器中横向滚动，局部滚动不得撑宽整个页面；不要求把复杂数据强行压缩到手机宽度而失去可读性。
- Dialog、Form、主要操作（primary action）及错误/警告反馈在代表 viewport 下必须保持可见、可聚焦、可操作；不得因 viewport 缩小把主操作永久推出屏幕、遮挡关键错误或形成无法完成的表单。
- 横竖屏或 viewport 尺寸变化不得静默丢失仍处于当前客户端状态中的合法未提交草稿。该原则适用于教师编辑类表单、学生提交类输入及后续具备合法未提交状态的页面；具体草稿字段、autosave / 持久化协议和客户端状态实现由届时对应 authoritative owner 与当前代码维护，本节不维护实现明细。
- 不得根据手机、平板、电脑、viewport width 或 orientation 推断 teacher/student role、authorization 或 route permission；角色与权限由正式 Auth / Route / Session 合同决定。
- 不要求不同设备像素级一致；允许布局根据空间合理重排，但必须保持信息层级、主要任务、核心操作、状态语义、可读性与可操作性。
- 当前正式基线使用上述 7 个代表 viewport，不穷举所有设备 × 角色组合。仅当真实产品或设备需求证明该集合不足时才调整，不因新增设备型号机械增加 viewport。
- 特定硬件能力如成为未来业务的真实依赖，由对应业务合同另行定义；本节只维护响应式设计责任。

本节建立稳定的响应式设计责任（stable responsive design responsibility），不代表当前全部 route 已完成响应式改造、全部页面已通过 7 个 viewport 验收，或已有 scripted Browser responsive regression、真实设备 evidence、Agent/Human smoke passed。当前实现能力以 [Frontend Snapshot](./handoff-frontend-snapshot.md) 与当前代码为准；测试资产、执行方式与证据状态由 [Frontend Testing Playbook](./handoff-frontend-testing-playbook.md) 维护。

## 6.2 公开入口与演示材料

- 公开入口保留 EduForge · 智炼品牌、浅色背景、中性正文、字体、圆角和轻边框。首页与 `/cases/*` 的标题强调、主按钮、链接、焦点及品牌标记使用协调的青绿：主要强调 `#0F766E`、白字主按钮 hover `#115E59`、氛围背景可用浅薄荷 `#F0FDFA`；保留错误/警告语义，不向登录及师生工作区扩展换色或修改全局主题。
- 首页以平台定位为主：桌面左侧约 55% 承载大标题、简短介绍与作品/独立说明/AI 辅助反馈/教师评阅特色，右侧单案例预览辅助说明教学理念；登录为主操作，左侧“查看协作案例”直接进入当前选中案例的完整详情，与右侧预览保持一致；顶部仅保留品牌与登录入口。案例名称作为可见切换入口，默认 OrbitPass、只手动切换；预览以工程问题大标题和简短引导语带出片段，人的审查用浅暖色底区分，保持青绿主题与平台介绍的主次关系。
- 在 `1536×864`、`1280×720` 与 100% 缩放下继续以一屏完整呈现为优化目标；减少留白、重复入口和文案，保持登录、案例与备案可达。手机按平台介绍在前、案例预览在后排列，低高度和放大阅读自然纵向滚动，不用整页隐藏溢出、裁剪、缩放或内部滚动面板制造一屏效果，可读性和内容完整优先。
- 案例详情自然纵向滚动，正文只含一个 h1；规则、审查与修订结论先于补充代码，不复用首页一屏目标。代码、表格与静态图示的收缩、局部滚动和无页面横向溢出遵循 [§6.1](#61-响应式与设备兼容基线)，不使用虚假产品截图或假操作界面。
- 详情案例导航沿用首页预览的分段视觉语言：灰底轨道、白底当前项、青绿文字与轻阴影；仍为跨页链接，不使用页内 ARIA tabs 语义。当前项以实际路径为依据，通过视觉强调和 `aria-current="page"` 表达，状态随路径更新，不以独立选择状态替代实际页面。
- 三个案例详情的顶部统一使用同宽、同间距和一致字级的标题卡，首行固定为“AI 协作编程案例”，随后呈现各自标题、简介及三枚关键词标签；卡片采用浅青绿底、细边框与圆角，标签使用白底。窄屏自然换行并由内容决定高度，不以固定高度或截断制造一致外观；共享组件职责见 [Component Map](./handoff-frontend-component-map.md#41-public-entry)。
- 六个步骤统一以序号与步骤标题在上、正文在下的纵向结构依次展开，使用一致分隔线和间距，步骤之间不并排；步骤内部可按材料关系展示时间轴、文件树与差异对照。代码、伪代码和文件树统一使用近黑背景、浅白等宽文字及相同字号、行高与留白，超长内容仅在代码区横向滚动。
- 关键规则、修订结论和验收依据直接可读，原生展开控件承载补充材料；保留文字状态、标题层级、键盘焦点与可读性，动效尊重减少动态效果偏好，不提供假运行按钮、模拟实时日志或虚构进度。
- 案例采用自然工程叙事，验证区以输入、触发条件、预期结果和判断依据呈现“验证场景与验收标准”，不把分析或推演写成实际测试通过；代码、说明参考与教师追问就近标注，不反复堆叠虚构/预置警示。共享详情布局以简短文字区分外部开发验证与 EduForge 的作品、独立说明和反馈承载能力；不伪造客户、交付、执行或学习成效。案例内容由对应组件维护，职责见 [Component Map](./handoff-frontend-component-map.md#41-public-entry)。
- 登录路径真实可用，不用未实现的注册、体验或联系入口代替；页脚平台署名与备案信息保持真实且处于次级层级，公开页备案链接仅在首页正常文档流页脚保留，案例详情与认证页面不重复展示。

## 7. 文案与信息边界

- 用户可见文案优先使用课程、班级、任务、提交、反馈等产品语言，不直接暴露字段名、内部阶段编号或后端错误实现。
- 必须展示技术状态时，先转译为角色可理解的含义；具有排障价值但非主要任务所需的信息应降低默认优先级。
- 页面不得通过夸大措辞把 AI Feedback 或分析结果描述为确定性教学结论。
- 同一概念、状态和动作在 Teacher/Student 主链路中保持一致命名，避免页面各自创造近义术语。

## 8. 当前与未来边界

- 本基线只描述当前 EduForge 公开入口与教师/学生产品形态能够支持的稳定原则。
- Learning Evidence Foundation、Task Workspace、Evidence Timeline 或其他未来设计概念，在尚未进入当前实现前，不得被视为现有 UI 能力、既定布局或当前组件合同。
- 具体实现状态以 [项目 Roadmap](./handoff-roadmap.md) 与当前代码为准；只有产品范围和实现事实稳定后，才更新对应 Owner 文档与本设计投影。

## 9. 维护规则

- 新增或调整页面、组件、布局、样式和用户交互前，先检查本文是否已有适用原则。
- 设计原则变化时更新本文；route、API、component 或当前实现事实变化时更新其各自 Owner，不在本文复制明细。
- 正式代表 viewport 集合或响应式/设备兼容设计原则变化时更新本文；测试资产、执行方式与 evidence 状态由 [Frontend Testing Playbook](./handoff-frontend-testing-playbook.md) 维护，本文不记录通过状态。
- 优先扩展已有可复用模式；只有重复需求和职责边界稳定时才新增公共组件。
- 遵循 `reference, don't restate`：没有设计职责变化时，本文件保持 zero diff。
