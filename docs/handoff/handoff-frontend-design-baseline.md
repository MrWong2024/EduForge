# EduForge 前端设计基线

## 1. 文档定位

本文是 EduForge 稳定前端产品、视觉、交互与 UX 原则的 Owner，用于约束后续页面、组件、布局、样式和用户可见交互。

- 当前前端工程结构和能力范围由 [Frontend snapshot](./handoff-frontend-snapshot.md) 维护。
- 当前路由、API 对接和组件职责分别由 [route map](./handoff-frontend-route-map.md)、[API map](./handoff-frontend-api-map.md) 与 [component map](./handoff-frontend-component-map.md) 维护。
- 本文不冻结具体 Tailwind class、色值或组件实现，也不把尚未实现的未来产品方向写成当前设计事实。

## 2. 当前产品与界面基线

EduForge 当前前端已形成教师端与学生端两个角色入口，共用轻量页面骨架、清晰标题层级和可复用的导航、空状态、错误状态与标签页模式。

- 教师端围绕课程、班级、任务、提交、反馈和教学分析组织工作。
- 学生端围绕加入班级、查看任务、完成提交和理解反馈组织路径。
- 当前视觉以浅色、中性、低装饰和高可读性为主；设计基线延续这一整体一致性，但不把现状误称为完整设计系统。

## 3. 核心产品原则

1. **教学任务优先于技术术语**：页面首先表达用户要完成的教学动作、对象、状态和下一步，不让 API、DTO、内部 ID、raw enum 或实现机制占据主要信息层级。
2. **信息层级清晰**：页面标题、上下文、主要状态、主要操作和辅助信息应有稳定顺序；复杂页面先给结论和行动入口，再按需展开细节。
3. **角色目标明确**：教师端服务快速判断与教学干预，学生端服务任务完成与反馈理解；同一技术能力应按角色使用目标呈现。
4. **一致性优先**：页面调整优先复用现有 Shell、PageHeader、Tabs、EmptyState、ErrorState、任务上下文和既有表单/动作模式。
5. **渐进改进**：没有明确产品收益时，不进行大范围视觉重写、布局体系替换或装饰性升级。

## 4. 教师端 UX 基线

- 优先呈现班级、任务、学生、提交和反馈的当前状态，以及教师可以立即采取的下一步行动。
- 看板与分析页面应帮助教师快速识别需要关注的对象和可执行干预，不用原始数据堆叠替代判断支持。
- 高频教学动作保持清晰可达；归档、删除、恢复等低频或高影响动作降低默认视觉权重，并保留明确确认与结果反馈。
- 统计与 AI 分析使用克制、可解释的教学语言，不把代理指标写成正式成绩、能力结论或因果判断。
- 复杂详情应保留来源、上下文和返回路径，避免教师在跨课程、班级、任务和提交时失去定位。

## 5. 学生端 UX 基线

- 优先提供从“看到任务”到“完成提交”再到“查看反馈”的连续路径，减少不必要分支和认知负担。
- 每个关键页面应突出一个主要下一步；辅助操作不得与任务主动作争夺视觉优先级。
- 截止、提交资格、处理进度、失败和可重试状态应使用学生能够理解的语言，并给出明确下一步。
- 空状态、错误状态和权限边界应说明发生了什么以及用户可以做什么，不要求学生理解内部实现机制。
- 反馈呈现优先帮助学生理解问题和改进方向，不以状态枚举、内部标签或调试数据作为主内容。

## 6. 视觉与布局原则

- 延续当前浅色背景、中性色层级、清晰边框和克制状态色；颜色服务于层级、状态和错误识别，不服务于装饰。
- 保持稳定内容宽度、合理留白和可扫描的信息分组；标题、说明、操作区和主体内容避免挤在同一视觉层级。
- 卡片、表格和列表按信息结构使用，不为了制造“仪表盘感”堆叠容器。
- 错误、警告和成功状态不能只依赖颜色表达；关键状态同时提供文字或明确语义。
- 页面与组件应延续现有响应式收缩和换行方式；密集内容需要局部滚动时，不得造成页面级无意横向溢出。
- 动效保持少量、短暂且有功能目的，不用复杂转场掩盖状态变化或增加等待感。

## 7. 文案与信息边界

- 用户可见文案优先使用课程、班级、任务、提交、反馈等产品语言，不直接暴露字段名、内部阶段编号或后端错误实现。
- 必须展示技术状态时，先转译为角色可理解的含义；具有排障价值但非主要任务所需的信息应降低默认优先级。
- 页面不得通过夸大措辞把 AI Feedback 或分析结果描述为确定性教学结论。
- 同一概念、状态和动作在 Teacher/Student 主链路中保持一致命名，避免页面各自创造近义术语。

## 8. 当前与未来边界

- 本基线只描述当前 EduForge 教师/学生产品形态能够支持的稳定原则。
- Learning Evidence Foundation Phase 1 仅在 [项目 Roadmap](./handoff-roadmap.md) 中处于 `PLANNED`；尚未成为当前 UI 能力。
- Task Workspace、Evidence Timeline 或其他未来界面不得因名称已出现而被视为已实现页面、既定布局或当前组件合同；只有产品范围和实现事实稳定后，才更新对应 Owner 文档与本设计投影。

## 9. 维护规则

- 新增或调整页面、组件、布局、样式和用户交互前，先检查本文是否已有适用原则。
- 设计原则变化时更新本文；route、API、component 或当前实现事实变化时更新其各自 Owner，不在本文复制明细。
- 优先扩展已有可复用模式；只有重复需求和职责边界稳定时才新增公共组件。
- 遵循 `reference, don't restate`：没有设计职责变化时，本文件保持 zero diff。
