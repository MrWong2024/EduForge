# Codex 指令生成规则 v1.20（精简稳定版）

> 适用于采用 `frontend\`、`backend\`、`docs\` 目录结构，并通过架构文档与规则文档约束开发的项目。
> 目标：保证指令结构稳定、输出可审核、执行边界清晰、文档同步可判断。

---

## 0. 适用主体与执行边界（全局总则）

本规范以 GPT 生成 Codex 指令为主要用途，同时包含 Codex 在真实执行阶段必须继承的治理规则。规则按明确主语、实际语义和所处阶段生效；Codex 阅读完整规范，不等于必须把其中所有生成期规则重新执行一遍。

- **GPT-only**：明确以 GPT 为主体，或本质属于用户需求分析、业务/接口/状态/数据合同锁定、Codex 指令骨架与栏目职责设计、篇幅控制、精简去重、生成前工具选型判断、最低充分性自检、初始验证风险候选与主要证据设计、实现前初始 A/B/C 的规则，只由 GPT 在生成期承担。Codex 将其视为上游来源，不得重新展开为第二套需求分析、合同设计、初始风险扫描、候选全集、指令自检、篇幅检查或独立审计阶段；只有当前任务明确将其中某项列为执行目标时例外。
- **Codex-only**：明确以 Codex 为主体，或属于真实执行期间当前仓库、工具、runner discovery 和运行环境门禁、实际实现、实现中新候选追加、实现后增量 A/B/C、实际与最终验收、覆盖完整性对账、实际 diff 核对、分级完成语义、执行期复杂度治理及范围失稳后的安全停止，由 Codex 执行。
- **Shared**：同一条款同时规定 GPT 与 Codex 职责时，GPT 只承担生成期部分，Codex 只承担执行期部分；双方不得复制对方已经完成的职责。主体判断不得机械扩大为某个完整章节全部只属于一方，因为同一章节可以包含共享职责。

Codex 阅读本规范，是为了理解任务治理边界、继承执行期规则并了解 GPT 已完成的上游设计前提，而不是在普通实现任务入口重做 GPT 的最低充分性自检、指令篇幅检查、初始候选全集、初始 A/B/C 或初始验收方案设计。Codex 也不得盲信已被真实证据否定的前提：当前代码、接口、配置、runner、环境、实际 diff 或执行证据证明前提失效时，应先确认真实事实，再按执行期增量治理在锁定合同内最低充分修正；合同无法唯一成立或范围明显失稳时安全停止并报告，但不默认从需求分析开始重做全部初始流程。

## 1. 固定前缀规则（必须存在）

所有交给 Codex 执行的任务指令都必须包含以下主体边界声明；涉及代码修改时还必须保留相应架构与规则文档引用：

```text
本指令中：
- 执行前阅读 docs/codex-instruction-spec.md 并按适用主体执行；明确属于 GPT 的需求分析、合同锁定、初始 A/B/C、指令生成与精简等生成期规则视为上游已完成，Codex 不得重复执行或扩展为额外流程。
- 若涉及修改 backend\ 目录下的代码，严格遵循 docs/backend-architecture.md 与 docs/codex-rules.md 的规范。
- 若涉及修改 frontend\ 目录下的代码，严格遵循 docs/frontend-architecture.md 与 docs/codex-rules.md 的规范。
- 若同时涉及修改 backend\ 目录和 frontend\ 目录下的代码，必须分别遵循对应架构规范。
```

此段为强制执行边界声明，不得省略。

---

## 2. 标准结构骨架（栏目固定）

每条 Codex 指令必须包含以下栏目，栏目名称固定：

1. 〖任务名〗
2. 〖任务目标〗
3. 〖实现范围〗
4. 〖接口与口径约束〗（如无则写“无”）
5. 〖强约束（必须遵守）〗
6. 〖非目标（明确不做）〗
7. 〖环境变量 / 配置项〗（如无则写“无”）
8. 〖实现步骤（建议按顺序）〗
9. 〖预期文件清单（新增/修改）〗
10. 〖文档同步要求〗（如无则写“无”）
11. 〖验收步骤（由 Codex 执行）〗
12. 〖输出要求（本次任务专用，用于审核）〗

---

## 3. 核心执行原则

### 3.1 骨架固定，内容弹性

* 栏目结构必须稳定。
* 栏目内部内容可根据任务类型扩展。
* 不允许新增随意的一级栏目。
* 不得删减固定栏目。
* 固定栏目用于保证信息分类稳定，不要求各栏目铺满；具体内容必须遵循 3.7 的最低充分设计、精简与去重规则。

---

### 3.2 文档同步要求必须显式判断

所有涉及代码、配置、接口、数据模型、路由、组件、测试或架构决策变更的 Codex 指令，都必须判断是否需要同步文档。

文档同步要求的执行规则如下：

* 若需要同步，必须明确列出需要更新的文档。
* 若不需要同步，必须在“〖文档同步要求〗”栏目中写“无”，不得省略。
* 同步范围可包括但不限于 `docs\` 下的架构文档、规则文档、测试文档，以及 `docs\handoff\` 下已经存在的交接文档。
* 不得要求创建与本次任务无关的文档。
* 不得假设某个 `docs\handoff\` 文件一定存在；生成具体指令时，必须以当前仓库实际存在的文件为准。

---

### 3.3 输出要求必须与任务绑定（关键原则）

“输出要求”不得使用固定模板，必须根据本次任务的风险点、审核重点和边界信息定制。

输出要求至少包含：

* 新增/修改文件清单
* 本任务的关键实现说明或关键代码片段（视任务类型而定）
* 文档同步情况
* 根据任务实际情况明确声明未涉及 `backend\`、未涉及 `frontend\`、未新增依赖、未修改接口、未修改配置等边界信息
* 逐项区分 Codex 已实际执行并通过、Codex 已实际执行但失败、因权限 / 工具 / 环境限制未执行，以及需要开发者完成的特定人工项

上述边界声明必须按任务实际情况定制，不要求机械输出全部声明。

仅提供命令文本但未实际执行，必须报告为未执行，不得记为通过；人工待签收、工具限制或其他 `not_executed` 状态也不得记为通过。

输出要求是本规则中最重要的审核锚点。

---

### 3.4 数据库任务声明（强制）

凡任务涉及数据库选择或隔离治理，或者会连接数据库、启动会连接数据库的应用或测试进程、准备或清理数据库 fixture，Codex 指令都必须完整声明以下字段；用途为 `none` 时也不得省略：

```text
数据库用途类别：
具体数据库映射来源：
允许数据库：
禁止数据库：
允许操作：
是否允许写入：
是否允许 cleanup：
是否需要长期保留 namespace：
进程与环境隔离要求：
连接后的实际数据库名门禁：
```

声明规则：

1. `数据库用途类别` 必须使用 `docs/codex-rules.md` 定义的 `none`、`development`、`standard_test`、`browser_acceptance` 或 `production_or_operations`。
2. `具体数据库映射来源` 必须指向项目 testing playbook、用户明确输入或其他明确项目文档，不得依据经验猜测。
3. `允许数据库` 和 `禁止数据库` 必须填写具体项目值，不能只写“测试库”“开发库”或其他模糊称呼。
4. `none` 类任务必须明确填写“不连接数据库”，并禁止无故启动应用或数据库相关进程。
5. 混合任务必须按独立子进程分别声明，例如普通 unit / E2E、Browser fixture、Browser test backend；每个子进程分别填写用途、允许数据库、禁止数据库、操作和门禁。同一任务同时涉及 `standard_test` 与 `browser_acceptance` 时，必须明确声明至少两个独立子进程：`standard_test` 子进程只能加载 `backend/.env.test`，`browser_acceptance` 子进程只能加载 `backend/.env.browser-acceptance`。两个文件可以同时存在于磁盘，但不得叠加加载到同一进程，也不得依赖 dotenv 加载顺序、shell 旧变量或后加载覆盖行为决定连接数据库。
6. 生成测试或本地人工冒烟任务指令时，必须区分 synthetic application account password 与真实 Secret。unit / E2E、Browser fixture 或本地人工冒烟创建的纯合成应用账号，只要专用于测试或人工冒烟、不对应真实人员、不复用真实密码、不具备生产或真实业务数据访问能力，且对应脚本具有正确的环境和数据库 fail-closed 门禁，其密码可以作为固定普通测试常量直接写入 tracked test、fixture、人工冒烟准备脚本或 Codex 指令；可以使用 `12345678` 这类简单值，不强制 ignored file、环境变量、剪贴板、随机生成、Secret Manager 或父进程注入。
7. 只要任务包含 Browser fixture 的 prepare、replace、prepared verify、Browser 登录或角色 Session、post-browser verify，指令仍必须确保同一 synthetic application account 在同一 namespace 生命周期内使用同一个确定密码值，并说明所有创建、认证或校验阶段使用的 tracked 常量或稳定配置；不校验密码的 cleanup 无需人为增加该依赖。指令必须禁止从数据库 URI、数据库用户密码、时间、进程值或无关 Secret 派生应用测试密码，也不得在不同阶段无故切换值。若已准备的 namespace 与当前固定值不一致，指令必须要求使用正确固定值显式执行受控 replace，再执行只读 prepared verify，并仅在通过后进入 Browser；不得通过反复 verify、手工改库、降低校验标准或虚报 prepared gate 通过来绕过。
8. 不得复用已设置数据库连接的 shell 上下文，也不得通过一个全局环境配置同时服务不同数据库用途。切换用途或复用 shell 前，应优先启动独立进程，或明确清除或覆盖数据库主连接变量、管理连接变量、项目定义的数据库用途变量及其他用途相关变量。具体变量名必须从项目级 testing playbook、项目环境约定、任务声明或用户明确输入中解析；通用指令规范不得硬编码项目专属变量名。这是数据库隔离门禁，不是要求每一步清空固定测试密码的保密仪式。
9. 符合第 6 条的 synthetic application account password 按普通测试常量自动使用；同一账号优先使用确定性固定值，指令不得机械要求一次性密码、每次重新生成、每 Profile 单独生成或逐次人工输入。
10. 数据库账号密码、完整 MONGO_URI / MONGO_ADMIN_URI、production / operations 凭据、真实人员账号密码、真实应用用户或业务主体认证凭据、可访问真实数据或非隔离环境的凭据、OSS AccessKey / Secret、ASR / LLM / SMS 等第三方 Secret 仍不得包含在指令、Git 跟踪文件、日志、manifest、截图、生成物、最终报告或提交记录中。该严格规则同样适用于 `standard_test` 与 `browser_acceptance` 的数据库账号密码；第 6 条只例外纯合成的被测应用账号密码。
11. 输出要求必须报告各子进程的实际数据库用途和实际数据库名校验结果；可以按任务需要报告第 6 条的 synthetic application account password，但不得输出数据库密码、完整连接串、Cookie、Session、token 或其他严格 Secret。
12. 如无法唯一解析用途或具体数据库，或连接后的实际数据库名与声明不一致，指令必须要求立即停止，不得自动回退到其他数据库。

### 3.5 验收执行主体与自动化责任（强制）

1. Codex 是默认验收执行主体。当前工具、权限和任务边界允许完成的全部验收步骤，必须由 Codex 实际执行，包括指令要求的 lint、typecheck、build、unit、E2E、fixture 生命周期操作、应用启动与健康检查、可可靠完成的 Browser 自动化，以及 Git diff、status 和范围检查。
2. 指令不得只列出命令、步骤或建议并默认要求开发者手动执行，也不得把整个验收阶段作为人工操作清单交还开发者。
3. 开发者批准权限提示、确认高风险命令或提供外部授权，只是 Codex 执行该步骤的前置条件，不改变执行主体；获得批准后，指令必须要求 Codex 继续执行。
4. 权限审查超时、命令未启动或执行许可未获得时，该步骤必须记为 `not_executed`，不得记为失败或通过；Codex 应请求必要授权，并在获得授权后重新执行，不得要求开发者复制命令到终端。
5. 命令已启动但退出码非 0 时属于实际执行失败。仅“已请求执行”“已获授权”或“已提供命令”均不构成验收通过。
6. 只有当前工具无法支持的实体设备操作、无法可靠产生或观察的原生交互、必须由人工完成且当前工具无法可靠替代的主观感知或专业判断、Codex 无法代替的外部登录 / 验证码 / 硬件 / 安全审批动作，或取得授权后仍因环境缺少必要工具或权限而无法自动执行的具体单项，才允许标记为需要开发者操作或授权。
7. 每个人工例外必须逐项说明 Codex 无法执行的原因、开发者需要完成的具体动作、需要返回的脱敏结果及该项的准确状态；不得因此把其他可自动化步骤一并转交开发者。
8. 人工结果返回后，Codex 仍负责继续完成后续可自动化验证和整体收口；不得用静态检查、模拟结果或文字声明替代确实需要人工完成的验收。

### 3.6 工具适配与安装前置判断（强制）

1. 生成 Codex 指令前，GPT 必须先判断当前任务是否已有成熟、可靠且与项目技术栈兼容的标准工具，并核对仓库现有工具是否已经足够。
2. 标准工具能够显著降低实现复杂度、提高验收可靠性或避免重复建设时，GPT 必须先向用户说明：工具名称、解决的问题、建议安装位置、是否新增项目依赖，以及为什么优于自研替代方案。
3. 新工具由用户负责安装，或由用户明确授权 Codex 安装。用户确认安装完成后，GPT 才能基于仓库中真实存在的版本、package 和锁文件生成后续 Codex 指令；未经用户明确授权，指令不得包含安装、升级或下载依赖的操作。
4. 不得因为标准工具尚未安装，就默认要求 Codex 自研等价基础设施；尤其不得为了避免引入成熟工具而自研 Browser runner、CDP WebSocket、测试框架、文档解析器或其他已有成熟方案覆盖的重复能力。
5. 项目现有工具已经足够时，不得机械建议继续安装新工具，也不得另建同类 runner、协议客户端或测试框架。
6. 工具选型必须考虑后续任务复用、维护成本和项目兼容性，不得只为当前单项临时拼接。
7. “某项事实需要真实 Browser 参与”只决定证据层，不自动推出“必须建设或维护 deterministic scripted Browser regression”。Browser execution mode 至少可以从 scripted deterministic Browser regression、Agent-assisted interactive Browser smoke、human manual / real-device smoke 中按 assertion target 选择；三者是执行方式，不是新的项目状态。
8. Playwright 或等价确定性 Browser runner 是 non-UI Browser runtime / network / origin / isolation semantic 的高价值长期回归工具，不是产品 UI regression 的默认工具。即使 UI interaction topology、selector、行为锚点或文案稳定，流程很短、重要或长期回归价值高，只要主要 assertion target 是产品 UI 结构、控件、组件层级、交互路径或用户 workflow，就不获得 scripted 资格。Agent-assisted interactive Browser smoke 只有在当前执行环境确实提供 Agent 可控制的真实交互式 Browser 时才可选择；它是客观 production UI Browser evidence 的默认执行方式，不是 scripted regression 失败后的降级版。人工或真实设备 smoke 独立承担主观、专业和真实硬件判断；Agent 不可用或人工操作本身属于验收合同时，客观 UI flow 也可以按真实 execution mode 由人工执行。
9. CI、持续自动回归或可复用 scripted evidence 的要求不能覆盖上述边界。需要 persistent CI 的风险必须先拆分为 pure / unit / HTTP E2E / verifier 可证明的业务不变量、可由 scripted Browser 证明的 non-UI Browser semantic，以及由 Agent-assisted 或 human 承担的剩余 UI behavior。若合同不可拆分地要求 deterministic scripted UI workflow，与本规范冲突时，Codex 必须停止并报告，由用户决定是否建立显式项目例外；通用规范不提供默认例外。

### 3.7 最低充分复杂度优先、指令精简与去重（强制）

1. **最低充分复杂度优先与最低充分性自检**

   GPT 在需求分析、任务或工作包拆分、架构与数据设计、测试设计以及生成 Codex 指令前，必须进行与当前任务规模和风险相匹配的最低充分性自检。

   “最低充分复杂度优先”是指：在满足业务目标，并保证数据完整性、权限、安全、隐私、正常主流程、不可逆业务事实、必要防重复和关键失败恢复的前提下，多个方案均能满足要求时，优先采用实现、测试和维护复杂度最低的方案。该原则适用于项目全生命周期，不限定一期，也不得被解释为可以为简单而牺牲正确性。

   长期权衡顺序固定为：

   1. 数据完整性、安全、权限、隐私和业务不变量；
   2. 正常主流程完整可用；
   3. 失败可解释、可恢复；
   4. 实现、测试、维护复杂度低；
   5. 用户便利和性能优化；
   6. 低频边缘场景下的无缝自动协调。

   这是方案权衡原则，不建立评分表、候选计分机制或新的项目状态体系。在前四项得到保证时，可以合理接受性能略低、多一次数据库读取、多一次 HTTP 请求、操作串行、用户多一次确认、主动刷新、重新点击或显式重试。不得仅为了少一次点击、更无缝、理论最优性能或极低概率异常的自动处理，增加明显不成比例的状态、组件、服务、跨模块依赖、异步协调或测试复杂度。

   应优先复用仓库现有能力，并判断拟新增的数据模型或持久化结构、字段、状态、接口、抽象、基础设施、配置、文档和测试资产，是否为当前已锁定交付目标所必需。

   凡没有当前需求、真实调用方、明确验收路径，且无现行安全、隐私、业务、数据、权限、合规或其他已锁定约束依据，仅服务于未来假设的内容，必须删除或延后。

   最低充分不得被用于省略或削弱当前任务已经锁定的业务或领域正确性、安全、隐私、数据完整性、权限、不变量、正常主流程、有副作用操作的幂等与防重复、关键失败恢复、兼容性、可审计性和可验证验收要求。

   该自检属于 GPT 在形成任务方案和 Codex 指令前进行的临时内部判断，不得演变为独立审计阶段、额外文档、固定长清单、持久候选仓库、额外状态机或 Codex 执行流程。

   涉及验证候选时，仍须按照 3.9 执行；本条不得替代、削弱或重复 3.9 的候选生成、治理、任务归属和最低充分证据选择。

   系统级允许正常并行：独立业务聚合或互不相关的业务实例不需要全局串行，读操作可以正常并发。同一业务聚合内部，在业务允许时优先一个阶段只有一个主要写入主体；存在多个角色或终端，不等于默认支持多个主体同时写同一聚合或实时协同编辑。

   “同一业务聚合内写操作串行优先”是业务交互与写入主体选择原则，不表示 Node 单线程、全局 mutex、MongoDB 全局锁、Redis 锁、`session locked` 字段、所有 HTTP 请求排队、分布式锁或 worker 全局串行，也不授权新增任何技术锁模型。

   真实竞争的长期默认处理为：一个合法写操作成功，另一个 stale / competing 写被安全拒绝；已成功事实不得被旧操作覆盖，不产生重复副作用；客户端重新读取服务端权威状态并给用户清楚提示，由用户显式决定是否重试。“一个成功 + 一个 CAS 安全拒绝”可以是正确结果，409 本身不是产品缺陷。只有无真实竞争的正常操作稳定冲突、数据丢失、重复副作用、权限或状态错误、无法恢复、服务端事实矛盾，才构成产品缺口。除非当前业务合同证明不可缺少，不默认建设自动 retry、自动 merge、自动 replay 副作用写、queue、lease、distributed lock、多套 revision 或 mutation coordinator。

   POST、PATCH、DELETE 等有业务副作用的操作遇到网络结果不确定、冲突或页面恢复时不得默认自动 replay；应先读取最新服务端事实，再由用户决定是否重新操作。测试工具内部的 Playwright 时序、Next prefetch、canceled GET、Console 网络噪声、精确事件到达顺序或自动化限制，不得在缺少业务风险依据时演化为新的产品状态、锁、配置、API、重试或状态机要求。

2. **单一事实原则**
   同一目标、范围、约束、非目标、文件清单、命令或验收结论只能在最合适的栏目完整描述一次。其他栏目需要关联时使用简短引用，例如“验收范围同〖实现范围〗”，不得换一种措辞重复全文。

3. **引用既有规则**
   架构、安全、Git、数据库和测试通用规则已经由项目文档明确规定时，指令应引用对应文档；除任务必须填写的具体数据库映射、任务特有风险、例外或参数外，不得复制整段通用规则。

   通用规则、架构和治理文档只定义跨项目可复用原则，不承载某个项目的具体业务角色、业务实体、业务流程、工作包状态或当前实现事实。项目专属事实应由项目级 handoff、代码、配置或任务合同维护；通用文档确需举例时使用抽象占位符或明确标记为通用示例，不得把示例写成当前项目事实。

4. **固定栏目不等于固定篇幅**
   固定栏目可以根据任务实际情况只写“无”或一至数条必要信息，不得为了形式完整填充无实际信息的套话。

5. **任务特有信息优先**
   指令正文重点保留本任务独有的业务契约、风险、修改边界、数据库值、验收命令和证据要求；通用背景和项目已知事实不重复铺陈。

6. **栏目职责去重**
   * `任务目标`：说明要解决的问题和最终结果，不在实现步骤中重复。
   * `实现范围`：说明允许读取、修改和新增的文件或目录。
   * `接口与口径约束`：只记录本任务特有的业务契约。
   * `强约束`：只记录违反后可能造成越界、数据风险或错误实现的任务特有约束。
   * `非目标`：只列容易被误做且确有必要排除的邻近范围，不得逐条反向复制强约束。
   * `实现步骤`：说明执行顺序，不重复目标和非目标。
   * `预期文件清单`：只列文件，不重复解释实现内容。
   * `文档同步要求`：只说明同步哪些文档及原因。
   * `验收步骤`：列 Codex 必须实际执行的检查和命令，不重复任务背景。
   * `输出要求`：只要求报告实际验收结果和关键证据，不再次复述完整任务说明。

7. **命令去重**
   同一命令不得同时出现在实现步骤、验收步骤和输出要求中。命令原则上集中放入验收步骤；实现步骤只描述执行动作，输出要求只要求报告结果。

8. **Codex 指令正文的软性篇幅参考**
   * 以下区间只适用于按本文生成的 Codex 指令正文，不适用于产品代码、测试代码、fixture、Browser spec、脚本、文档同步代码或任何单个实现文件，也不是任何实现资产的验收门禁。
   * 单点修复或纯文档任务的 Codex 指令正文：通常约 80～200 行。
   * 常规单层功能任务的 Codex 指令正文：通常约 150～400 行。
   * 跨前后端、数据库或完整测试闭环任务的 Codex 指令正文：通常约 300～800 行。
   * Codex 指令正文超过约 800 行时，应优先检查是否存在重复、是否可引用既有规则、是否应按稳定契约拆分阶段。
   * 上述区间仅用于指令正文的规划和复查，不是通过、失败或停止门禁；不得为了满足行数删除必要的任务特有信息，也不得把这些区间转写为具体任务的代码行数预算。

9. **合理超出**
   多数据库用途、多个独立 Browser Profile、复杂迁移、不可逆数据操作或大规模验收矩阵确有大量互不重复的信息时，可以超过参考区间；但每段内容必须对应独立风险、契约或证据，不得通过重复措辞制造篇幅。

10. **不得过度压缩**
   精简不得省略 Secret 保护、数据库用途与实际数据库名、数据库隔离、安全边界、Browser fixture 的凭据与生命周期要求、权限、不变量、不可逆语义、并发、幂等、错误口径、cleanup、关键验收、人工例外边界、验收真实性和 `not_executed` 状态要求。

11. **生成前自检**
    GPT 输出指令前必须检查：
    * 是否有同一要求在三个以上栏目重复。
    * 是否完整复制了项目规则文档。
    * 是否把强约束机械反写成非目标。
    * 是否在输出要求中再次复述任务全文。
    * 是否可以在不损失信息的前提下删去重复段落。

### 3.8 命令与运行环境前置核验（强制）

本节属于 Shared 门禁，分别约束 GPT 的生成期命令设计与 Codex 的执行期 discovery；Codex 对当前真实仓库和环境的再次确认是执行门禁，不是重新进行需求分析或初始测试方案设计。

**GPT 生成期命令设计**

1. GPT 如需在 Codex 指令中写入具体定向测试或跨进程验收命令，必须依据真实 package script、runner 配置、对应 testing playbook 和直接相关的运行环境配置，设计工作目录、调用链、环境初始化和参数入口。
2. GPT 不得根据命令外观或工具通常行为猜测参数透传；无法在生成期可靠证明追加参数会进入目标 runner 时，应要求 Codex 在执行期完成 discovery 并使用项目已验证的调用入口，不得虚构具体命令。

**Codex 执行期门禁**

3. Codex 正式执行前必须根据当前真实仓库再次确认 package script、runner 配置、工作目录、调用链、环境初始化和参数入口；不得因 GPT 已做生成期核对而跳过当前运行环境门禁。
4. 定向测试必须先使用 runner 的 discovery / list 能力获取测试文件集合；只有 discovery 结果与预期目标完全一致时，才能正式执行。
5. 跨进程验收必须先核对页面与服务的协议、host、port、CORS origin、Cookie host / domain 语义，以及公开构建变量等构建时输入；声明值、构建产物和实际请求必须一致。
6. 测试选择器或参数透传错误属于测试命令缺陷；origin、CORS、Cookie 或构建输入不一致时必须先停止业务验收并排查环境或配置链，不得直接归类为产品缺陷。修正环境、完成所需重建并规范启动后仍可复现的合同违例，必须按证据重新分类为产品代码或受版本管理配置缺陷，不得永久豁免。
7. 测试范围未经证明时，不得据此判定目标通过或失败；因命令错误而未执行目标测试时记为 `not_executed` 或项目既有等价状态。
8. `unknown` 仅表示命令已经启动但因超时且无可靠摘要、输出不完整或证据不足而无法判断的临时测试结论，不是项目持久状态。具体 Audit 或验收项状态必须遵循项目 testing playbook，不得将 `unknown` 写入项目状态清单。
9. 项目级 discovery、正式运行和跨进程编排方法必须引用对应 testing playbook，不在通用指令规范中复制具体命令或环境值。

### 3.9 验证候选生成、必要性、可达性与证据选择前置核验（强制）

**适用主体与双时点分工（本节唯一权威定义）**

- GPT 在生成实现指令前负责锁定业务、接口、状态和数据合同，依次执行初始阶段 A、B、C，并将最低充分结果中的当前阻断候选、初始主证据、可复用证据、具名后续阶段和人工边界传递给 Codex。
- Codex 接到实现任务后，按已锁定合同实施，在实现中追加新候选，完成后执行增量阶段 A，对新增或实质变化项执行增量阶段 B、C，再执行最终验收和覆盖完整性对账。Codex 不得把“再次执行初始 A/B/C”增加为任务入口的固定前置阶段。
- 当前代码、API / DTO / Schema、package script / runner、运行环境、实际 diff 或执行证据证明 GPT 的初始前提失效时，Codex 应先按执行期职责确认真实事实：属于正常新增或变化风险时进入增量治理；能在锁定合同内最低充分修正时继续；导致合同无法唯一成立或范围明显失稳时安全停止并报告。新证据可以否定前提，但不默认触发从需求分析开始重做全部初始 A/B/C。

验证候选生成负责避免遗漏，候选治理负责避免过度测试；顺序必须是先生成、再治理。不得因已有分类、证据复用和最低充分证据规则而省略生成，也不得因新增生成规则而删除或削弱既有治理。

阶段 A 是风险扫描，不是自动待办生成器。发现新候选必须先经过阶段 B、C 治理，不能因工具报告、理论交错或候选刚被发现就自动扩大 production 实现、测试矩阵或当前任务范围。

**阶段 A：系统生成验证风险候选集合**

本节统一使用以下术语：

- **实现单元**：具有独立锁定范围和验收合同的开发单元，包括 A# 后端能力、B# 前端能力、工作包内明确编号的子任务、跨前后端实现任务、会改变正式行为合同的缺陷修复，以及其他具有稳定边界的模块。实现单元不要求同时包含前后端。
- **阶段**：同一实现单元因合同锁定、前后端顺序、并发、恢复、Browser fixture、外部权限、设备或环境等原因拆出的明确执行阶段。阶段不是新的候选仓库，也不是无期限延后方式。
- **工作包或产品能力**：由一个或多个 A#、B# 和跨层任务共同形成的产品范围；其状态继续由项目 roadmap 维护。

候选生成、治理、任务归属、即时验收和覆盖对账同时适用于 A#、B#、工作包子任务、跨层缺陷修复及其他具有明确合同边界的实现单元。

`初始验证风险候选集合` 是指：相对于当前已经锁定的业务、接口、状态和数据合同，系统识别出的全部具有独立风险意义的验证候选。可以简称为“候选集合”。合同尚未锁定时，必须先锁定合同或拆分设计阶段，不得用猜测同时生成实现和验收。

实现前的候选生成，以已锁定的目标业务合同、目标接口合同、状态与数据合同、当前既有代码、预计新增或修改的资产及预计影响范围为依据。对于当前代码中尚不存在、将在本任务中新增的 Controller、Route、DTO、Schema、mapper、页面、组件或其他资产，应核对其目标合同、调用边界、允许与禁止行为及计划形成的数据或外部副作用，不得将目标合同核对表述为已经核对实际实现，也不得因目标资产尚不存在而跳过对应风险来源。

这里的“全部”是风险级系统扫描，不是所有角色、字段、错误码和状态的笛卡尔积，不是 UI、API、unit、E2E 与 Browser 层的重复排列，不是为每个文案、按钮或数据库字段建立永久测试项目，也不要求达到特定数量或为每个候选分配 Audit ID、A# / B# 活动 ID。候选颗粒度限于独立业务风险、不可替代状态语义、权限/安全/隐私边界、数据副作用与不变量、已知回归风险，以及自动化无法替代的人工或真实设备边界。

GPT 对以下任务必须在生成 Codex 实现指令前执行候选生成：

- 新增或改变产品行为。
- 新增或改变页面、路由或用户流程。
- 新增或改变公开 API、DTO、Schema、权限或 ownership。
- 新增或改变状态机、不可逆动作、版本链、恢复、幂等或并发。
- 新增或改变数据库写入、audit、protected facts 或外部副作用。
- 修改公共 Guard、mapper、coordinator、状态管理、认证、Cookie、构建变量或其他横切合同。
- 修复可能改变正式行为边界的产品缺陷。

纯文档、纯格式和无行为变化的机械重构可以按实际影响执行简化扫描，不机械生成完整候选集合。

阶段 A 按本节前部主体分工在两个时点执行。GPT 在生成期执行初始阶段 A，以目标合同、当前既有资产、预计修改范围和预计影响为核对对象；Codex 在执行期完成实现后执行增量阶段 A，以实际落地资产、基线至当前工作区的实际 diff、新增文件、真实调用关系、共享资产影响和实际副作用为核对对象。Codex 不在任务入口重复初始阶段 A。以下八类来源在各自主体对应的时点均必须核对。某类目标资产在实现前尚未生成，不等于可以跳过该类来源，而应先依据已锁定目标合同生成初始候选，并在实现后根据真实代码态补充、修正或确认。

候选生成至少系统核对以下八类来源：

1. **业务合同**：用户目标、人工角色、正常路径、阻断路径、明确非目标和不存在能力。
2. **页面与用户流程**：路由和入口、可见性、表单和输入、writing / disabled、错误恢复、刷新、当前会话事实与持久事实。
3. **公开接口合同**：Controller / Route、Guard / Pipe、DTO / whitelist、ownership、客户端可控字段与服务端生成字段、response 和 mapper 隐私。
4. **状态与生命周期**：readiness、状态转换、幂等、合法并发、部分完成、显式恢复、网络结果不确定、相邻生命周期写保护、replacement 或版本关系。
5. **数据副作用与不变量**：允许变化、protected facts、audit、归属实体、业务来源、外部存储或其他外部副作用、rollback 或明确不回滚、verifier 与 cleanup 必要性。
6. **共享与横切边界**：认证和权限、公共 Guard / mapper、coordinator / writing lock / identity、Origin / CORS / Cookie、构建时变量、数据库用途和进程隔离。
7. **已有证据和变化影响**：unit、HTTP E2E、Browser、verifier、已知缺陷和回归，以及证据形成后相关代码、接口和配置是否变化。
8. **自动化边界**：真实设备、触控笔和手写、相机、打印、外部登录或硬件，以及无法可靠自动化的主观或专业判断。

候选集合原则上是 GPT 生成 Codex 指令时的临时设计工作集，不要求完整输出给 Codex，不要求写入 Testing Playbook，不要求长期分配 ID，也不要求随提交持久保存。持久文档只保留通用生成和治理规则、当前明确未关闭的真实 `gap`、当前人工或真实设备项目、当前批次状态、精确证据资产和 evidence commit，以及具有长期意义的合同结论；详细执行与治理过程由 Git 历史追溯。

**阶段 B：候选治理和最低充分证据选择**

阶段 B 的必要性、可达性、证据复用和最低充分证据规则，同时适用于初始阶段 A 形成的候选、实现中即时追加的候选，以及增量阶段 A 新形成或发生实质变化的候选。增量候选不得因发现较晚而降低治理标准；初始候选也不得因已经写入 Codex 指令而免于根据真实变化重新治理。

系统生成后的候选风险必须先按项目 testing playbook 判断属于正式 UI、公开 API、合法并发、内部损坏、真实设备或通用门禁中的哪一类，并执行以下核验：

1. 为每个强制测试写明真实触发路径、调用方或人工角色、实际接口与足以阻断发布的业务风险；无法证明必要性的测试不得写入指令。
2. 检查相关代码、接口与配置未变化时是否已有可复用的精确证据；不得为同一风险重复建设 Browser、HTTP E2E、verifier 或多个 Audit ID。
3. 选择最低充分证据层：页面或用户流程候选不因用户可见或 UI 可达而自动要求 Browser，应按项目 testing playbook 选择最低充分证据。必须 Browser 时先判断 assertion target：BrowserContext、Cookie / Storage、origin、CORS / credentials、必要 Browser lifecycle、独立 Browser-native API semantic，或不依赖复杂用户点击的 production build / 真实 origin / 真实 HTTP 最低充分 wiring，属于 non-UI Browser semantic，可以继续评估 scripted；产品 UI 结构、文案、visible controls、组件层级、locator、interaction topology、用户操作 workflow、页面级 restore / resume 体验及 accessibility / 视觉体验属于 UI semantic，客观事实默认由 Agent-assisted 验证，主观、专业或真实设备事实由 human manual / real-device 验证。公开 API 绕过由 HTTP E2E 验证，合法并发以 HTTP E2E 为主，局部判断和非阻断防御分支使用 pure/unit。
4. 不把只能直接改库、伪造内部对象或篡改运行时形成的异常默认列为阻断性业务验收；只有正式导入、迁移、兼容合同、已知生产事故或明确合规要求可以升级。
5. 页面没有操作入口、但仍可通过 Postman、curl 或自编客户端直接调用公开 API 的非法操作，由后端 HTTP E2E 验证，不重复建立 Browser 场景。缩减 Browser 测试时，必须确认认证、权限、DTO 白名单、资源归属（ownership）、状态门禁、幂等、原子性、隐私和数据库无副作用等后端风险已有可靠证据；已有精确证据直接引用，只有存在真实缺口时才补充测试。
6. 没有穷举所有角色、错误码、字段组合和数据库快照，不等于存在测试缺口；只有风险真实可达、风险独立且当前最低充分证据缺失时，才能标记为 `gap`。
7. 要求完整 unit、E2E 或 Browser 套件时，必须说明认证、公共 Guard、Schema、通用 mapper、公共测试基础设施、跨模块合同或其他具体影响依据；不得只写“为了保险”。

**Browser 证据执行方式与合同自证防线**

1. Browser evidence requirement 与 Browser execution mode 必须分开判断，且先问“assertion target 是 Browser semantic 还是 UI semantic”，不能先问 Playwright 是否能写。scripted deterministic Browser regression 默认只准入 non-UI Browser runtime / network / origin / isolation semantic；主要测试逻辑和主要断言不得依赖 production UI 的 DOM 结构、文案、selector、visible controls、组件层级、interaction topology 或用户操作路径。
2. non-UI Browser semantic 包括 BrowserContext isolation、Cookie isolation / persistence、localStorage / sessionStorage / IndexedDB 等 Storage isolation、origin isolation、CORS / credentials、浏览器层 Session / Cookie 生命周期、navigation / reload / history / origin 的 Browser lifecycle 本身、Browser-native file / blob / object URL semantics、独立 Browser-native API semantics，以及 production build / 真实 origin / 真实 HTTP topology 的最低充分 wiring。production 页面可以作为 Browser runtime 宿主，但 scripted 主断言不得因此扩张成登录、多页导航、多次点击、modal / details、录音、手写、上传或业务完成等 UI golden path。
3. Browser-native API 名称本身不构成 scripted 资格。MediaRecorder、Canvas、Pointer、file input、focus、keyboard、clipboard、permissions 等都必须继续判断是在证明独立 Browser primitive，还是产品 UI 使用该 primitive 的行为；前者只有在可脱离 production UI topology 的薄 profile 中才可 scripted，后者属于 UI。navigation / reload 只有在证明 Cookie / Storage / Context 等 Browser lifecycle 事实时可 scripted；业务页面刷新后的题目、面板、按钮、提示和继续操作体验属于 UI。泛化的 file input 以及 keyboard / focus 不再是默认 scripted 白名单。
4. UI semantic 包括页面结构、可见组件或控件、文案、提示语、modal / drawer / details / tab、组件展开关系、selector / locator / DOM ancestor、元素位置、enable / disable、用户点击顺序、输入 / 保存 / 继续流程、页面级错误恢复、UI reload / resume、frontend workflow，以及视觉、布局和 accessibility 体验。客观 production UI Browser behavior 默认使用 Agent-assisted interactive Browser smoke；Agent 可以适应当前布局、DOM ancestor、展开结构、动态控件和不改变合同的普通 copy 变化，但不得改变预先冻结的 expected contract。通过只能记录为 `Agent-assisted Browser smoke passed`，不能记录为 scripted / Playwright regression green、CI coverage 或 reusable scripted evidence。
5. human manual / real-device smoke 独立负责可理解性、自然性、视觉层级、主观体验、专业判断、真实设备和真实麦克风、触控笔、相机及浏览器 / OS 权限体验。Agent Browser 不可用或人工实际操作本身是验收要求时，客观 UI flow 也可以形成准确标记的 human manual evidence；不得与 Agent-assisted 或 scripted 结果混称。human 不替代 BrowserContext、Cookie / Storage isolation、CORS / credentials 等独立 non-UI Browser security semantic 的 scripted evidence。
6. substantive contract change、旧 scripted Profile 与 current 行为广泛漂移，或准备重写 / 替换 Browser spec 主体时，GPT 必须先从已锁定产品合同、current roadmap contract、正式 API / DTO、领域原始需求或用户明确决策等独立来源冻结 expected business behavior，之后才读取 current production code 获取 selector、testid、route、控件结构和 wiring。Agent 的适应性不得形成“production 怎么实现 → test 就期待什么 → test 再证明 production 正确”的自证闭环。该冻结默认只是 GPT 生成期的临时设计工作，不机械新增审计任务、JSON、hash 或长期文档；只有合同来源矛盾、旧测试与 current 合同严重冲突或重写依据无法明确时，才建立具名 read-only independent contract audit。
7. 对现有 scripted Profile，`patch / rewrite body / retire` 前先判断其是否仍有本版本 scripted 资格。主要验证 UI 时直接选择 `retire scripted profile / switch current UI evidence to Agent-assisted or human`，不得 patch selector 或 rewrite scripted UI body 作为长期方案；历史通过继续按形成时有效的 historical evidence 保存，但不自动构成 current / future scripted regression 资格。只有 `ELIGIBLE_NON_UI_SCRIPTED` Profile 才继续依据职责、漂移范围与维护成本选择 patch 或 rewrite；真正 Browser-only semantic 被长 UI flow 包裹时，先尝试下沉低层或形成最低充分的薄 non-UI profile，无法合理薄化时由 Agent-assisted 验证整个 UI flow。

**验收优先级与冻结止损**

1. 验收先证明正常 happy path：正常用户按正常步骤从入口走到正常结束。happy path 未完成前，不持续扩大低频异常矩阵。随后依次选择少量高价值防御、代表性恢复和工作包最终收口项；该顺序不新增测试阶段，不改变初始 / 增量 A、B、C。
2. 自动化失败必须先分类为 product、spec/test、fixture、support/runner、environment 或 tool limitation，并依据证据修正对应层。GET aborted、Next prefetch、Playwright response / requestfailed 时序、测试鼠标坐标和 runner 编排问题，不得在没有稳定业务合同违例时升级为产品 `gap` 或 production 架构要求。
3. 只有 normal happy path 失败；数据完整性受损；权限、安全或隐私违例；正常单次操作稳定出现未知 4xx / 5xx；当前业务合同直接违例；或没有可信恢复路径，才默认重新打开当前实现。测试基础设施、环境和工具问题只修对应测试层；低频非阻断候选可以具名归入工作包最终收口。
4. 当 happy path 已通过、当前阻断项已关闭、剩余候选均有明确主要归属和复核时点时，冻结当前实现单元的验收范围。不得为了让候选集合在理论上再也发现不了新风险而递归扩张；冻结只停止无界扩张，不删除候选、不降低工作包最终完成门禁，也不削弱数据、权限、安全、隐私、不可逆事实、防重复和关键恢复证据。
5. UI scripted Profile 不需要等待失败两轮：静态审计已经证明主要 assertion target 是 UI semantic 时，直接判定不符合本版本，不再执行、patch selector 或修复 scripted UI body。连续两轮止损继续适用于真正 `ELIGIBLE_NON_UI_SCRIPTED` 的测试基础设施：同一 execution mode 与资产方案因 spec/test、fixture、support/runner、environment 或 tool limitation 连续两轮失败后，不得进行第三轮同方案 patch / rerun，必须在修复或重写合格的 non-UI scripted Profile、退役 Profile、Agent-assisted smoke、manual / real-device smoke 中重新选择最低充分方案。明确的 production contract violation 仍按产品 `gap` 处理，不得用工具重选掩盖。

阶段 B 还必须在上述既有治理中判断候选是当前实现单元阻断项，还是工作包最终收口候选；这只是候选归属与验收时点判断，不是新的项目状态、候选仓库或阶段状态机：

- **当前实现单元阻断**：普通主流程不可达；数据错误、丢失或重复；权限或隐私问题；正常单次操作持续出现未知 4xx / 5xx；用户无法继续；直接违反当前实现合同；或没有可信恢复路径。满足任一项必须在当前实现单元关闭。
- **工作包最终收口候选**：低频并发恢复、多种异常组合、代表性但不影响核心操作的 accessibility 改进、真实设备专项，或已有低层强证据但尚缺高层补充验收，可以不阻断当前子阶段。转入最终收口时必须指定具体工作包和重新核对时点，不得静默删除或无期限延期，并须在对应工作包完成前重新核对。

正常主流程优先不表示忽略边缘风险。候选仍按阶段 A 先生成，再按阶段 B 治理并选择最低充分证据，最后按阶段 C 明确归属和关闭条件；不得另建数据库式候选仓库或第二套验证流程。已有 unit / HTTP E2E 已充分覆盖的边缘状态组合，不要求在每条高层 Browser 主链中重复排列。

具体分类、证据复用、执行范围、fixture、Stage、verifier 与 Browser Profile 规则引用 `docs/handoff/handoff-frontend-testing-playbook.md` 和 `docs/handoff/handoff-backend-testing-playbook.md`，本规范不复制项目完整分类表或命令。

**阶段 C：任务归属、分级完成、即时验收与最终收口**

实现前阶段 C 确定的是候选的初始主要归属和预期关闭条件；实现后和最终验收后，必须依据实际代码、证据和剩余 `gap` 重新执行归属与关闭判定。具体关闭条件遵循下述“已有归属与已经关闭”。

**已有归属与已经关闭**

1. 每个独立候选必须获得且只能获得一个主要归属：本次 Codex 任务新增验收、引用已有精确证据、当前实现单元的明确后续阶段、同一工作包中具名的其他实现单元、人工或真实设备验收、`supplemental defensive / compatibility`，或当前不可达/明确非目标/退休项。支持证据可以分层，但同一风险不得在多个证据层重复建立主测试。
2. `已有归属` 只表示候选的责任边界已经明确，不表示 `已经关闭`。候选分配给后续阶段、另一个实现单元或人工项目后，在对应关闭条件满足前仍保持 open；不允许用未命名的“以后前端”“以后后端”或“以后再看”制造虚假归属。
3. 候选只有在以下任一条件成立时才能视为关闭：
   - 当前代码态下的对应验收已实际执行并通过。
   - 已有精确证据仍适用于当前代码、接口和配置。
   - 经治理后准确归类为 `supplemental defensive / compatibility`、当前不可达、明确非目标或退休项，且不构成当前锁定范围的阻断验收。
   - 当前锁定范围要求的人工或真实设备验收已经实际签收。
4. 仅分配给后续自动化阶段、自动化测试仍为 `pending`、mandatory 人工或真实设备验收尚未完成、仍存在阻断性 `gap`，或证据形成后相关合同已发生影响性变化时，均不得写成候选已经关闭。

**默认即时验收与分阶段**

1. 实现前写入 Codex 指令的是基于当时合同和代码事实形成的“初始最低充分验收集合”，不是封闭的最终验收清单。实现后增量扫描产生新候选，或证明原证据层不再充分时，经阶段 B、C 治理后，可以补充验收、合并重复验收、以等价或更充分证据替换原验收，或扩大必要的验收范围；替换或合并时必须说明原候选由何种等价或更充分证据关闭，不得删除仍然适用的原始阻断性验收。实际实现没有覆盖某项已锁定合同，只能构成实现缺口，或者先重新锁定合同与任务范围；不得因为最终代码未实现某项合同，就把对应风险从候选集合或验收范围中删除。
2. 默认执行模式为“实现与即时验收一体化”。一个正常规模的 A#、B# 或其他实现单元，Codex 默认在同一任务中完成：
   1. 按初始合同实施。
   2. 实现期间追加新候选。
   3. 实现完成后执行增量阶段 A。
   4. 对新增或变化候选执行阶段 B、C。
   5. 执行最终验收。
   6. 完成候选覆盖完整性对账。
   7. 同步状态和证据。
3. 默认一体化不表示所有工作必须塞入一个巨大 Codex 指令，不禁止拆分 Browser、并发、迁移或独立验收阶段，也不表示代码已实现后必须在原任务中无限扩大测试范围。新实现单元默认仍不得采用“先开发、在 Playbook 积累、以后集中测试”的流程。
4. 实现期间随时发现的新风险必须立即加入临时候选集合，并继续按阶段 B、C 分类、归属和判定关闭。实现完成后、最终验收范围冻结前、宣布当前阶段或实现单元完成前，Codex 必须主动执行增量阶段 A，至少核对基线至当前工作区的实际代码 diff、新增和删除文件、公开合同变化、调用链和依赖关系变化、公共 Guard / mapper / coordinator / fixture 或其他共享资产变化、数据库 / Storage / 审计及其他外部副作用，以及实现和测试执行结果暴露的新状态、恢复路径、并发窗口或回归风险。新增或发生实质变化的候选必须重新执行阶段 B、C；最终验收暴露的新独立风险也必须先治理，只有命中“验收优先级与冻结止损”的重新打开条件才扩展当前实现，其他候选具名归入后续阶段或工作包最终收口。当 happy path 已通过、阻断项已关闭且剩余候选均有明确归属时执行最终覆盖完整性对账并冻结范围；不得规定无意义的固定循环次数，也不得对未变化候选机械重复相同测试。
5. 范围复杂或验收链路较重时，可以采用 `A# 实现阶段 → A# 独立验收阶段`、`B# 实现阶段 → B# 独立验收阶段`，或同一实现单元下其他具名且边界稳定的等价阶段。适合考虑拆分的原因包括实现范围或跨层调用链较大；新状态机、合法并发、部分完成或恢复复杂；数据迁移、兼容或不可逆副作用；Browser fixture、多个 Profile、跨进程编排或真实 wall-clock 验收本身构成独立工程；外部权限、设备或环境暂不可用；实际 diff 和新增候选显著超出初始预计，导致单任务边界不再稳定。这些阶段不产生新的候选仓库，也不改变 A# / B# 的最终完成门禁。
6. 具名实现阶段仍必须完成当前阶段拥有的实现、与实现紧密相关的即时安全门禁、实际 diff 增量扫描、新增候选的阶段 B、C 治理，并将未执行候选指向具名独立验收阶段或其他明确边界。实现阶段只能声明“当前实现阶段完成”，不得据此宣布 A# / B# 实现单元完成。独立验收阶段负责以实现阶段后的真实代码态为依据重新核对候选、复用仍然适用的已有证据、完成剩余自动化候选、执行最终覆盖完整性对账，并判定实现单元是否完成；分阶段不得退化为在 Playbook 长期堆积候选项。
7. 如果实际 diff、共享资产影响或新增候选显著超出初始预计，导致当前任务不能继续保持稳定、可审核和可回收的边界，Codex 不得因任务已经开始而无限扩大范围。Codex 应完成安全停止，报告实际变化和新增候选，并建议拆出具名后续实现、修复或独立验收阶段。已经完成的阶段证据可以保留，但不得用阶段完成替代实现单元完成。不得为该判断建立固定文件数、代码行数或测试数门槛；复杂度判断继续遵循 3.10 的职责、耦合、生命周期和维护成本口径。
8. 独立验收阶段发现生产合同违例时，必须准确分类为产品 `gap`。除非该任务在生成指令时已经明确包含产品修复范围，否则不得在独立验收任务中临场修改生产合同并自行宣布通过；默认应记录产品 `gap`、停止对应候选收口、建立具名修复阶段，并在修复后执行定向复验或恢复独立验收。测试资产、fixture、locator 或环境编排缺陷仍可在验收阶段按当前 testing playbook 规则修正。

**分级完成门禁**

1. **当前任务或阶段完成**只有在当前阶段拥有的实现已完成、当前阶段拥有的验收已实际通过、本阶段发现的候选均有明确主要归属、未在本阶段执行的候选已指向明确后续阶段/其他实现单元/人工边界或具名工作包最终收口、没有未披露的当前阻断 `gap`，且当前阶段状态和证据已同步时才能宣布。明确后续自动化阶段或工作包最终收口候选仍 `pending` 可以允许当前子阶段完成，但不能据此宣布对应工作包完成。
2. **A# / B# 或其他实现单元完成**只有在该实现单元锁定范围内的当前阻断候选和即时自动化验收均已关闭、所有属于本单元完成门禁的后续自动化阶段均已完成、不存在未披露的阻断性 `gap`、引用证据仍适用于当前代码态、当前范围 mandatory 的人工或真实设备项目已经完成、最终候选覆盖完整性对账已完成，且状态和证据索引已同步时才能宣布。尚未关闭的候选只有经阶段 B 治理为具名工作包最终收口候选、具有明确归属和复核时点时才可保留；它们不阻断当前实现单元，但在实际关闭前继续阻断对应工作包完成。
3. **工作包或产品能力完成**只有在工作包锁定范围要求的相关 A#、B# 和跨层任务均已完成，跨层合同、联调和用户流程验收均已关闭，范围内不存在 `pending` 自动化验收或阻断性 `gap`，mandatory 人工或真实设备项目满足工作包合同，且 roadmap 已按真实证据同步时才能宣布。Testing Playbook 不得自行启动或关闭 roadmap 工作包。

**A#、B# 与范围限定边界**

- A# 后端实现单元通常以 Controller/API、DTO/Guard/Pipe、Service/Repository、Schema/index、原子写、幂等、并发、恢复、audit、mapper、数据库终态和外部副作用为主要范围，并按风险从 backend unit、HTTP E2E、database verifier 与 static gate 中选择最低充分证据；没有正式 UI 入口时不机械新增 Browser。
- UI 行为明确属于同一工作包中具名的后续 B# 时，UI 候选可以归属该 B#；A# 在锁定的纯后端范围全部关闭后可以准确写为 `A# 后端范围完成`。该 UI 候选在对应 B# 验收通过前仍是 open，且不得据此宣布完整产品能力或工作包完成。若 A# 锁定合同本身包含跨层产品闭环，则不得把 UI 候选转移到未明确的未来 B# 以提前完成。
- B# 前端实现单元通常以页面/路由、用户入口、表单交互、Browser 状态、当前会话和持久事实、刷新/错误恢复、DOM/URL/Storage/Cookie/Network 隐私及代表性可访问性为主要范围。相关 A# 精确证据仍适用于当前代码态时，B# 应引用该 unit、HTTP E2E 或 verifier 证据，只为新增风险补最低充分 Browser evidence，并继续按 assertion target 选择 mode：non-UI Browser semantic 才可 scripted，客观 UI 默认 Agent-assisted，主观、专业或真实设备事实归 human；B# 改变后端合同或暴露新的公开调用路径时，必须重新扫描后端候选，并明确由当前跨层实现单元或具名 A# 承担。
- mandatory 人工或真实设备项目尚未完成时，不得无条件宣布完整范围完成。当前合同明确只验收桌面、自动化、后端或其他子范围时，可以使用“桌面范围完成”“自动化范围完成”“后端范围完成”等准确限定语；不得将限定完成简写为无条件的“A# 完成”“B# 完成”或“工作包完成”。

本节后续规则的执行主体以本节前部“适用主体与双时点分工”为准，不得将任一生成期规则解释为要求 Codex 重复初始 A/B/C，也不得将该分工解释为允许 Codex 跳过增量治理或最终验收。

Codex 指令不要求包含或输出完整候选全集，也不得新增第 13 个固定一级栏目；但必须在现有 12 个固定栏目中传递足以支持 Codex 完成增量治理和最终对账的关键候选与边界，不能只存在于 GPT 未传递的临时思考中。

最终报告只报告实际新增并执行的验收、引用的关键已有证据、明确未执行/人工项和剩余 `gap`；不要求输出已淘汰、合并或复用后的完整候选表。

### 3.10 实现与测试资产复杂度治理（强制）

本节属于 Shared 复杂度规则：GPT 在方案、指令和测试设计期使用本节防止设计过度；Codex 在实现与测试资产实际增长过程中使用本节控制职责、耦合、生命周期和维护成本。双方分别在自己的阶段执行，不重复对方已完成的流程，也不建立第二套复杂度审计。

1. 产品代码、测试代码、fixture、Browser spec、contract spec、verifier、脚本和文档同步代码不得以物理行数、非空行数、净新增行数或接近某个行数阈值作为硬性或接近硬性的复杂度门禁。行数不得单独决定是否通过、失败、停止实现、压缩、拆分文件或允许同步文档，也不得要求“超出即停止”“低于才通过”或“压缩到预算内才验收”。
2. 行数只能作为可选、非阻断的观察信号。文件变长、新增代码较多、测试资产体积增长或单文件维护压力上升时，可以触发结构复查，但数字本身不能证明设计过度，也不能单独要求压缩或拆分；判断必须回到职责、重复、耦合和维护成本。默认不在最终报告统计物理行、非空行或净新增行数，只有用户明确要求、需要诊断复杂度变化或真实外部规则存在时才报告，并明确该数字不是单独的验收结论。
3. 禁止为满足行数或文件数量指标而合并无关语句、使用难读的一行表达式、删除必要注释、类型、错误处理或安全检查、缩短具有业务意义的命名、压缩格式或绕过 formatter、把代码搬入无关文件、创建无实际职责的 helper、把独立职责强塞进一个文件，或用字符串、动态代码、生成代码隐藏复杂度。
4. 复杂度必须按语义评估：职责是否内聚；是否重复建设 runner、fixture、manager、Stage、verifier、manifest 或已有 helper；是否新增不必要的跨模块依赖和隐式调用链；状态、分支、恢复路径与并发窗口是否对应真实风险；进程、端口、环境变量、数据库用途、Secret 传递和 cleanup 生命周期是否必要且可稳定回收；命名、类型、注释、错误处理和修改入口是否清楚；新增证据是否覆盖此前未被可靠证明的独立风险。
5. 测试基础设施明显超过被测业务、重复建设既有机制、职责明显混杂、跨进程或 cleanup 链路无必要扩张、相同逻辑重复实现，或当前方案已无法安全维护时，仍必须暂停继续扩张。暂停依据必须说明具体职责、依赖、状态、生命周期和风险；随后检查能否复用现有能力、按稳定合同分阶段或沿清晰职责边界拆分，并向用户报告推荐方案，不得用压缩或指标规避继续过线。
6. “最多一个 CLI 和一个 spec”等文件数量限制只能用于阻止重复基础设施，不能迫使不相干职责共处、在单文件复制逻辑或放弃合理拆分。文件数量限制与清晰职责边界冲突时，必须停止并报告设计冲突，由用户决定，不得通过塞入代码或偷偷搬移文件规避。
7. 只有真实外部硬约束才允许精确大小限制：用户明确给出的硬性格式要求；已经存在且实际启用的编译器、平台、协议、提交系统或 linter 强制限制；外部接口或文件格式明确规定的大小限制。GPT 或 Codex 不得自行创造、推定或把观察指标包装为外部限制。
8. 最终报告不得把“满足行数预算”作为实现或测试资产的验收结果。项目级 Browser、fixture、E2E、verifier、cleanup、证据复用与止损细节分别引用 `docs/handoff/handoff-frontend-testing-playbook.md` 和 `docs/handoff/handoff-backend-testing-playbook.md`，不在本节重复。
9. Browser fixture、support、runner 和 verifier 不是任何 Browser evidence 的固定配套。只有 Browser 需要独立合法 synthetic 起点、Browser 写入终态未被更低层证据充分证明，或确有 namespace / cleanup 隔离风险时才增加对应资产；不得为了把 UI flow 改造成 scripted 而扩张 fixture、support、testid、test-only UI hook、复杂 Browser harness 或第二套业务状态模型。当这些资产开始复制 catalog、业务状态或服务端判断并逐步形成“第二套实现”，维护工程明显超过所证明的 Browser 风险，或 UI flow 需要大量基础设施才能稳定时，必须停止继续扩张并回到 3.9 重新选择 evidence execution mode；后者进一步支持 Agent-assisted / human，而不是用更多资产追求 scripted green。

### 3.11 文档事实所有权与同步写入门禁（强制）

1. **单一权威 owner**：GPT / Codex 在新增或更新长期文档事实前，必须先轻量判断“哪份现有文档完整维护这条事实”。项目已有文档职责定义时以项目定义为准。每个 persistent fact 只允许一个 authoritative owner，可以有多个 projection / reference 文档，但不得由多个平级 owner 同时维护同一 current contract；不得为了让当前读者方便、让单份文档自包含或方便下一会话而复制完整事实。
2. **`reference, don't restate`**：目标文档不是 owner 时，默认只保留其职责所需的当前状态、高层摘要、必要依赖、owner 链接或历史时间定界。除非缺少它会使目标文档自身职责无法成立，否则不得重新复制详细字段、状态转换、逐项矩阵、API / DTO 细节、测试数量、revision、fixture shape、媒体 cardinality、完整错误矩阵或完整业务流程。
3. **“同步文档”不等于复制事实**：先更新 authoritative owner，再判断其它 projection 文档的状态、索引、依赖、引用或投影是否因该变化而改变；只有其自身职责发生变化时才修改，没有职责变化的文档保持 zero diff。“同步相关文档”不得解释为在所有相关文档重复写一遍新事实。
4. **completed work package compression**：roadmap / plan 在规划或开发中可以保留足够的目标、依赖和完成定义；工作包正式 completed 后，必须主动压缩为高层目标、高层交付摘要、高层完成定义、权威合同链接和测试证据入口。实现过程流水、子任务逐条日志、具体 fixture / Browser 结果、revision / count、临时 workaround，以及已由 contract、map 或 testing playbook 完整拥有的详细规则应删除或回到各自 owner。
5. **current stage 不是 release notes**：roadmap 的 current stage / current phase 只回答已完成、进行中、待开始、当前阻断、下一工作包和必要阶段级特殊状态；不得长期积累子阶段实现日志、逐轮 Browser 结果、测试 count、已关闭缺陷或历史诊断。
6. **去重不等于信息丢失**：authoritative owner 已完整保留某事实时，从非 owner 删除重复副本属于 deduplication，不是 information loss；不得以“可能以后有用”为由永久保留重复 current 副本。
7. **历史事实按职责归档**：决策背景归 decisions，测试通过和 historical evidence 归 testing playbook，实现演进归 Git，范围变化归 roadmap 的范围处置记录，稳定业务合同归 contract。不得为了保留历史而让 current section 同时维护当时事实、current 事实和修订说明。
8. **轻量 owner check**：普通任务只需在设计和执行期完成上述轻量判断，不得为每次文档修改生成 owner audit JSON、长期 ownership registry、新状态机、额外审批流程或独立文档数据库。只有 ownership 矛盾、多份文档均声称唯一事实源或大规模治理时，才需要具名 read-only 文档审计。
